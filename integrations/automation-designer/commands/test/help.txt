Usage: wi-impl ad test <UUID> [flags]

Execute an Automation Designer method for testing and inspection.
This really runs the chain (SQL steps commit, HTTP steps call out), so it
requires an explicit --env.

The uuid runs its OWN body: a PUBLISHED uuid runs the published copy, even
after `ad save` changed its draft. data.ranVersion names the copy that ran
(PUBLISHED v5, DRAFT v6), and a warning says when the published uuid's draft
has unpublished changes (pass the draft uuid to run them). A step that calls
another method always runs that method's PUBLISHED copy: a warning names
every callee whose draft has unpublished changes. A step marked async is
started and really runs (with its side effects) but is not awaited: it is
warned about, listed in the confirmation, and shown 'dispatched (async)'.

ad test posts to the platform's test route, not the execute route the app
(and `ad run`) uses, and the two hand some inputs over differently (live):
JSON text in a JSON-typed input reaches the method as an object here but as
text through `ad run`; an object value arrives here as a Java Map
(toString() gives {a=1}) but as a JSON node ({"a":1}) through `ad run`.
Text inputs holding JSON text are the same on both. ad test warns when an
input is sent either way; confirm such behaviour with `ad run`.

Arguments:
  <UUID>                The UUID of the method to test (usually the draft).

Flags:
  --inputs <FILE|JSON>  Input values: a JSON file, or an inline JSON object
                        ('{"name":"World"}'), as `ad run` takes its payload.
  --input <KEY=VALUE>   One input value (repeatable), applied on top of --inputs
                        or --case. Typed by the method's input type (non-text
                        types parse as JSON). An unknown key is INVALID_INPUT.
                        Without --inputs/--input/--case the values are prompted
                        for (refused with --llm).
  --case <FILE>         Take the inputs AND the expectations from a test-case file
                        (`wi-impl ad test-case export` format, or a UI test-case body):
                        every `{output, op, expected}` assertion is checked locally.
                        Any other assertion (raw SpEL) cannot be checked here: the
                        run then exits 1 with AD_TEST_NOT_CHECKED, never ok:true.
                        Inputs stored as `{}` ("no value") run as null, as in the AD
                        screen. Cannot be combined with --inputs.
  --cases <FILE>        Run the method once per case in FILE: a JSON array, or JSONL
                        (one object per line), of {name?, inputs?, expect?[]} where
                        expect uses the --expect syntax. --input and --expect apply
                        to every case. Every case is a REAL execution (N cases, N
                        sets of side effects), so it confirms first, showing the
                        case count (--yes, required with --llm). Every row's inputs
                        are checked before anything runs. A progress line per case
                        goes to stderr (`case 12/86 PASS name (1.2s)`). A run that
                        fails with an auth / network / gateway error (e.g. another
                        session refreshing the same login) is retried once; if it
                        fails again the row is ERROR with error.tool: true, counted
                        in summary.toolErrors (a tool error, not the method). Prints
                        one row per case; exit 1 with AD_TEST_CASES_FAILED when any
                        case fails. With --compare-published every case also runs
                        on the published copy, right after its draft run, and its
                        row gains compare{…}. Cannot be combined with --inputs,
                        --case or --repeat.
  --trace               With --cases: each row also carries its trace and timing
                        (and so does compare.published).
  --expect <OUT=VALUE>  Check a method output after the run (repeatable). Operators:
                        = != ~= (contains) !~= (does not contain) > < >= <=;
                        `out=[…]` / `out={…}` compare JSON; `out.a[0]=x` looks inside JSON,
                        `out.size()=3` checks a list's (text's) size. ~= on a list
                        matches text inside any item. An empty or null output has
                        no value on the wire: it is reported as null and equals
                        `out=`, `out=null`, `out=[]` and `out={}`.
                        The value is JSON when it parses, else text; quote it
                        ('42') to compare as a string. "…" is a JSON string, so
                        \" \\ \n are decoded ('msg="Say \"hi\""' expects
                        Say "hi"); '…' is taken as typed. A quoted JSON text
                        ('{}') equals an output holding that JSON. Any failure
                        exits 1 with AD_TEST_EXPECTATION_FAILED.
  --compare-published   Also run the same inputs against the published copy (a draft's
                        referenceId, or the draft of a published uuid) and compare.
                        This EXECUTES TWICE — the DRAFT first, then the PUBLISHED
                        copy, both with real side effects, one through the
                        production body — so it asks for confirmation (--yes,
                        required with --llm). Nothing is restored in between: a
                        method that writes leaves both runs' rows, and the
                        published run sees the draft run's (wi-impl warns when a
                        db step writes). identical means the same status, HTTP
                        status, failing step and error, and outputs; when both
                        runs fail at the same step with the same error their
                        partial outputs are not compared (outputsCompared:
                        false). Expectations and the draft run's status decide
                        the exit code.
  --ignore <PATH>       With --compare-published: leave a value out of the output
                        comparison (repeatable). out (the whole output), out.a.b,
                        out[0].b, out[].b (b in every item), *.key (key at any
                        depth, every output): e.g. --ignore '*.updatedAt'.
  --ignore-order        With --compare-published: compare lists as sets (the same
                        items in another order are equal).
  --repeat <N>          Run N times (1-100) and report data.repeat {runs, serverMs,
                        wallMs}, each {min, median, max, values[]} (the server's
                        total time and the wall time); the rest of data is the
                        first run's. N real executions: confirms (--yes with
                        --llm). A progress line per run goes to stderr. Not with
                        --cases or --compare-published.
  --yes, -y             Confirm --compare-published's second (published) execution,
                        the --cases executions, or the --repeat runs.
  --verbose, -v         Print each step's outputs and the SQL it ran. (A command
                        flag here: it does not switch on runner debug logging.)
  --raw                 Include raw execution payload in output.
  --help, -h            Show this help message.

Global Flags:
  --env <name>          Set active environment. Required explicitly: this
                        really executes the chain. Any env from `wi-impl envs`.
  --llm                 Output structured JSON envelope for scripting/LLM use.

Notes:
  - Exit 1 with AD_TEST_FAILED when the (draft) execution FAILED, with the
    full data (failedStep, trace); AD_TEST_EXPECTATION_FAILED wins when an
    expectation failed. The message names the step, the HTTP status the
    run answered (statusCode: 403 for a refusal, as `ad run` would) and the
    step's own message.
  - "Something went wrong. Failed to execute automation!" is the platform's
    error with no reason. It has been seen on this route (at a database
    step) while `ad run` worked, and passing again later; failedStep.hint
    and the message say so. Retry, or check with `ad run`.
  - A non-2xx answer from the test route is TEST_EXECUTION_FAILED, with
    details like `ad run`'s EXECUTION_FAILED (decoded body; a body over
    16 KB is saved whole under ~/.wi-impl/logs/errors/, details.bodyFile).
  - Posts {category, jsonDefinition, id, uuid, version} to /chain/test with
    testValues set and automationApiId filled on every step (lean chains).
  - Data: ranVersion {uuid, state, version, label}, status, statusCode,
    outputs {code: value} (every method output),
    trace, expectations {total, passed, failed, results[]}, compare
    {draftUuid, publishedUuid, order ["draft","published"], identical,
    mismatches[] (status, statusCode, failedStep, outputs), differences[],
    outputsCompared, ignored?{paths, order}, draft{status, statusCode, timing},
    published{status, statusCode, outputs, failedStep, trace, timing,
    expectations?}}, repeat?.
  - With --cases, data is {uuid, ranVersion, publishedUuid?, cases[{name,
    pass, status (SUCCESS, FAILED or ERROR), statusCode, outputs, failedStep,
    expectations[], error?{code, message, tool?}, retried?, trace?, timing?,
    compare?{identical, mismatches[], differences[], outputsCompared,
    published{status, statusCode, outputs, failedStep, trace?, timing?,
    error?}}}], summary{total, passed, failed, toolErrors, identical?,
    different?}}. failed counts every case that did not pass, toolErrors
    included. A case whose run throws (compile error) is status ERROR; the
    other cases still run.
  - data.trace rows: {step (the step's orderIndex, a number, as `ad show`
    numbers it), automationId, description, status, totalTime ("26ms", "-"
    when the server gave none), timeMs (number or null), loop?, async?,
    errorSummary?}. There is no orderIndex key: match on step.
  - Per-step outputs are in data.serviceResults[{step, status, outputs[{code,
    value}], sql?, renderedInputs?[{template, rendered}]}]: sql is the SQL a
    db step really ran, every #{...} filled in (--verbose prints it).
  - data.timing {executionMs, totalMs}: the server's run times, numbers.
    A loop step's time covers all its iterations (the server reports no
    iteration count); it arrives in ns labelled ms, which wi-impl corrects.
  - Status 'dispatched (async)': an async step was started, not awaited (the
    server may call it not executed). It really runs, with its side effects.

Examples:
  wi-impl ad test 4a1b2c3d... --env <env> --inputs ./in.json --expect greetingOut='Hello World'
  wi-impl ad test 4a1b2c3d... --env <env> --input name=World --expect 'greeting=Hello, World' --llm
  wi-impl ad test 4a1b2c3d... --env <env> --case ./cases/greet.ok.1.json --compare-published --yes --llm
  wi-impl ad test 4a1b2c3d... --env <env> --cases ./cases.jsonl --yes --llm
  wi-impl ad test 4a1b2c3d... --env <env> --cases ./cases.jsonl --compare-published --ignore '*.updatedAt' --ignore-order --yes --llm
  wi-impl ad test 4a1b2c3d... --env <env> --inputs ./in.json --repeat 5 --yes
  wi-impl ad test 4a1b2c3d... --env <env> --inputs ./test-data.json --verbose --raw
