Usage: wi-impl ad test-case <action> [args] [flags]

Manage persistent test cases attached to an AD method's test suite. Every
write is read back from the suite and compared with what was sent
(AD_TESTCASE_VERIFY_FAILED when it did not land).

Actions:
  list <uuid>                             List test cases: the same structured result
                                          as wi-impl ad test-cases ({testSuiteId, testCases, total})
  create <uuid> --name <n> [--description <d>] [--input k=v]... [--assert out=v]...
  create <uuid> --file <case.json> [--assert out=v]... [--dry-run]
                                          Create one test case (UI encoding; refuses a
                                          name already in the suite: AD_TESTCASE_EXISTS).
                                          data.id is the new case's id
  update <uuid> <testCaseId> [--file <f>] [--input k=v]... [--assert out=v]...
                                          Replace a case's inputs/assertions. The name
                                          cannot change (AD_TESTCASE_FIELD_NOT_UPDATABLE);
                                          neither can the description: a file without
                                          one keeps it, a different one is kept as on
                                          the server with a warning (data.descriptionKept)
                                          and the rest is still updated
  delete <testCaseId> [--uuid <u>] [--yes]
                                          Delete a test case. data names the env;
                                          with --uuid it first checks the case is in
                                          that method's suite on this env
                                          (AD_TESTCASE_NOT_FOUND otherwise) and names
                                          the method, suite and case. A migrated
                                          method keeps its uuid and case ids on every
                                          env, so --env alone decides which one
  bulk <uuid> --file <cases.json> [--yes] Create an array of test cases (one POST each);
                                          the file may also be an `export` backup
  run-suite <uuid> [--yes]                Trigger the server's suite run (async: e-mail report
                                          only, not observable from the CLI)
  run-suite <uuid> --wait --yes [--case <name>]... [--match <text>]
                                          Run every active case now (one /chain/test run
                                          each), evaluate its assertions, and return a
                                          per-case PASS/FAIL/ERROR/NOT_CHECKED summary.
                                          --yes is required with --llm (it executes the
                                          method: AD_CONFIRMATION_REQUIRED without it)
  delete-suite <testSuiteId> [--yes]      Delete a test suite
  export <uuid> --dir <root> [--prune]    Write the suite to <root>/<Category>/<method>/
                                          (method.json + cases/<name>.json); read-only
  export <uuid>                           Without --dir: print the suite as JSON on stdout
                                          ({chainUuid, env, method, total, cases}), so
                                          `> backup.json` saves a backup that
                                          `bulk --file backup.json` restores. Plain JSON
                                          even in an agent session; --llm wraps it in
                                          the envelope
  sync <methodDir> [--uuid <u>] [--apply] [--prune] [--drop-unknown-inputs] [--yes]
                                          Diff the case files against the suite (dry run);
                                          --apply creates/updates them

Flags:
  --file <path>         Test case JSON: a case file (see below) or a UI test-case body
                        (create, update); an array of them (bulk).
  --name <name>         Test case name (create). Convention: <method>.<scenario>.<outcome>.<n>
  --description <text>  Test case description (create).
  --dry-run             create: check the case (contract, name not taken) and return
                        the body it would POST, {dryRun, name, body, warnings}: the
                        stored SpEL is body.assertions[].conditionExpression. Writes
                        nothing (it reads the target env, so --env is required).
  --input <k=v>         Input value (repeatable). STRING/TEXT inputs keep the text;
                        other types parse as JSON when they can.
  --assert <out=v>      Assertion (repeatable): out=v, out!=v, out>v, out<v, out~=v
                        (contains), out!~=v (does not contain). v is JSON when it
                        parses; quote it ('42') for a string. The left side may be
                        `out[0].col` or `out.size()`. A list or {} compares with =
                        and != (out=["a","b"], out=[], out!=[], out={}): the server
                        compares the output's compact JSON text, so item order
                        and number form (1 vs 1.0) must match. A non-empty object
                        cannot be compared whole (the server prints it as a Java
                        map): assert its fields (out.key=v).
                        Stored as the SpEL the server evaluates: `#{out} eq 'v'`,
                        `#{out} ne v`, `#{out.toString()}.contains('v') eq true`
                        (eq false for !~=), `#{out.toString()} eq '["a","b"]'`.
                        (`neq` and an infix `contains`, stored by wi-impl before
                        0.3.1, score ERROR on the server: they read back as raw
                        expressions with a warning; re-save the case to fix them.)
  --dir <path>          Export root (export). Without it, export prints the suite JSON.
  --uuid <uuid>         Chain to sync to (sync). Default: method.json uuids[<env>].
                        delete: the method the case must belong to.
  --wait                run-suite: run the cases now and wait for every result
                        (exit 1 unless all pass: AD_TESTCASE_SUITE_FAILED when a case
                        failed or errored, AD_TESTCASE_NOT_CHECKED when the only
                        problem is assertions wi-impl could not evaluate;
                        AD_TESTCASE_NONE when the suite has no active case).
  --case <name>         run-suite --wait: run only this case (repeatable; an unknown
                        name is AD_TESTCASE_NOT_FOUND before anything runs).
  --match <text>        run-suite --wait: run only the cases whose name contains the
                        text (with --case: either matches). data.skipped counts the
                        active cases left out.
  --apply               Perform the sync (without it sync only prints the plan).
  --prune               export: delete case files no longer on the server;
                        sync: delete server cases that have no file.
  --drop-unknown-inputs sync: leave out the inputs the method no longer declares
                        (in memory; the files are not changed), listed in
                        data.droppedInputs. Without it such a case is refused
                        (AD_TESTCASE_CONTRACT unknown-input) on --apply.
  --yes, -y             Skip the interactive confirmation prompt (write actions)
  --help, -h            Show this help message.

Global Flags:
  --env <name>          Target environment. Required explicitly for every action
                        except list and export (they write; a dry-run sync
                        reads the env it would write to, so it needs it too).
  --llm                 Emit a JSON envelope; --yes is required for writes in this mode.

Case file (one per test case; stable key order; no ids, so it can live in a
separate git repo and sync to any env):
  {
    "name": "greet.ok.1",
    "description": "greets World",
    "inputs": { "name": "World" },
    "assertions": [ { "output": "greetingOut", "op": "eq", "expected": "Hello World" } ]
  }
  "op" is eq, neq (or ne), gt, lt, contains or notContains; "output" may carry
  a path and .size() ("rows[0].label", "rows.size()"). "expected" is a scalar,
  or with eq / neq a list or {}.
  Assertions wi-impl cannot parse stay verbatim as {"expression": "..."}. Inputs whose
  stored wrapper carries more than {"value"} keep it in "inputExtras".

Sync plan: create (only in files), update (inputs/assertions differ: PUT),
drift (only the description differs: reported, the API cannot change it),
delete (--prune: only on the server), extra (only on the server, left alone),
conflict (duplicate name on the server). A description that differs (drift,
or with an update) is never written: data.descriptionNotApplied names those
cases and a warning says so; to change one, rename the case in its file and
--prune the old one. Names are never released: DELETE is a soft delete, so a
deleted case's name cannot be created again (AD_TESTCASE_NAME_RESERVED) —
rename the file's case instead. The suite lists only active cases, so the dry
run cannot see such a name (data.notes says so); --apply runs creates and
updates first and, if any fails, skips every delete (AD_TESTCASE_SYNC_SKIPPED)
so the suite is not left short.

Warnings (data.warnings / problems, kind text-input-braces): a TEXT/STRING
input that holds the text "{}" runs as that two-character string, not as
"no value"; remove the input to leave it unset (create, update, bulk, export,
sync).

run-suite without --wait (live): /testsuite/execute returns at once
("you will receive an email"); `ad test-report` is not per chain and stays all
zeros; the suite's executionStatus stays PASS even when an assertion fails, and
no case carries a result. Use --wait to see results: data {mode:"wait", total,
passed, failed, errored, notChecked, cases[{id, name, status, execution, outputs,
assertions{total, passed, failed, results}, unevaluated, warnings?, failedStep?,
error?}]}. Assertions wi-impl cannot evaluate (raw SpEL other than the stored
forms above) are listed in `unevaluated`, and the case is NOT_CHECKED, never
PASS. Inputs stored as `{}` ("no value", which every method save writes into
cases that did not set an input) run as null, the way the AD screen runs them.

Examples:
  wi-impl ad test-case create 4a1b... --name greet.ok.1 --input name=World --assert "greetingOut=Hello World" --env <env> --yes
  wi-impl ad test-case run-suite 4a1b... --wait --env <env> --yes --llm
  wi-impl ad test-case run-suite 4a1b... --wait --case greet.ok.1 --case greet.mars.2 --env <env> --yes --llm
  wi-impl ad test-case export 4a1b... --dir ./unit-tests/ad --env <env>
  wi-impl ad test-case export 4a1b... --env <env> > backup.json
  wi-impl ad test-case sync ./unit-tests/ad/Sandbox/greet --env <env> --apply --yes --llm
