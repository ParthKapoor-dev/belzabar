Usage: wi-impl ad save [FILE] --uuid <UUID> --env <env> [flags]

Save a JSON overlay onto a method's DRAFT through the V2 route
(GET /chain/v2 → overlay → POST /chain/v2). A PUBLISHED uuid is switched to
its linked draft (draft guard). You write only the change; wi-impl fills the V2
boilerplate (uuids, contract ids, encodings, UI defaults).

Arguments:
  [FILE]                JSON overlay (optional when --sql-file/--code-file carry
                        the change). Keys (anything else → AD_OVERLAY_UNKNOWN_KEY):
                          name, summary, description
                            (`description` writes the long method description,
                            V1 `methodDescription`; `summary` is the short
                            summary. `ad show` prints them as
                            summary.methodDescription / summary.summary.)
                          scope "UNRESTRICTED" | "INTERNAL_ALL_SERVICE" |
                                "INTERNAL_SERVICE" |
                                {"value": "INTERNAL_SELECTED_SERVICES",
                                 "services": [category name or uuid, …]}
                            who may call the method (the AD UI's Scope;
                            permissions.methodScope, the services as
                            allowedCategories). Read back with `ad show`
                            (summary.scope) or `ad state` (scopes).
                          parsedSteps[] {orderIndex, source|sql|expression|description}
                          ops[]   structural ops, applied in order:
                            {"op":"add-step", "after":N | "before":N, "step":{STEP}}
                            {"op":"remove-step", "step":N}
                            {"op":"move-step", "step":N, "after":M | "before":M}
                            {"op":"update-step", "step":N, "set":{STEP fields,
                                                  "removeOutputs":["fieldCode"]}}
                              set.outputs MERGES: it upserts by fieldCode (the
                              `as` name) and keeps every other output; use
                              "replaceOutputs":[…] (same format) to make the
                              step's outputs exactly that list, or removeOutputs.
                              Variable links: replaceOutputs also replaces
                              them (a listed output without var loses its
                              link); in outputs, "var": null unsets one.
                              set.service "Svc/method" points a service step
                              at another method (e.g. a renamed callee): the
                              step keeps its id, condition, exit, loop and
                              account; inputs/outputs whose key the new callee
                              has are kept (rebound to its contract), the rest
                              are dropped and listed in applied. Re-map in the
                              same set (inputs, outputs). Not for custom code,
                              nor between db_service and another service.
                            {"op":"set-input"|"set-variable"|"set-output", "key":K,
                             type?, required?, description?, default?}   (upsert)
                            {"op":"remove-input"|"remove-variable"|"remove-output", "key":K}
                              A method output stored without a key (older
                              methods; every run fails "key is null") is
                              named by its fieldCode: set-output K repairs it
                              in place (adds the key, keeps its uuid), and
                              remove-output K removes it.
                        Step numbers N/M are ALWAYS positions in the fetched draft
                        (as `wi-impl ad show` prints them), whatever other ops do.
                        after:0 = first; no anchor = append.
                        STEP (compact; the same format `ad create` takes):
                          service "Svc/method" | code "<js>" | sql "<SQL>"
                          codeFile / sqlFile   path, relative to FILE
                          inputs {"key": value, "body.nested": value}  (null removes)
                          outputs ["key"] | [{key, as, var, type}] | {"as": "key"}
                            as = the name the method sees; var = write it to a variable
                          when "<SpEL>" | null        entry condition
                          exit {onFailure, code, message}
                          exitIf {when, code, message} | null   conditional exit
                          loop {over:"#{list}"} | {times:n} | {while:"<SpEL>"} |
                               {from,to,by} (+counter, parallel, threads) | null
                          account <id|nickname> (db_service; may be omitted
                            only when the service has exactly one account on
                            the env — otherwise AD_OVERLAY_INVALID lists them
                            as id=nickname), description, language, async
                          (descriptions are rich text in the AD UI: `<` and
                          `>` outside HTML tags are stored as &lt; / &gt;, so
                          "{<name>: value}" shows as typed; <b>, <br>… stay
                          tags)
                          executor CODE_LAMBDA | INTERNAL_SERVER  (custom code;
                            a top-level STEP / set key, not inside customCode).
                            The CC5 warning "NODEJS_LAMBDA is deprecated" is
                            fixed by {"op":"update-step","step":N,
                            "set":{"executor":"CODE_LAMBDA"}}
                        sql alone picks db_service/data.read|add|update|delete
                        from the verb. Input/output keys are checked against the
                        callee contract (online, cached 1 h). A key the
                        cached contract lacks is re-checked online before
                        the save is refused (a callee just published with a
                        new input works at once); `ad publish` also drops
                        the method's own cached contract.
                        Refused with AD_OVERLAY_NOT_APPLIED because the server
                        drops them: buttonLabel, internalMethod, testValue, a
                        variable's BASE_64 encoding, input/output keys the callee
                        does not have, unknown services/accounts, a field on a
                        step of another kind. Code and SQL are plain text; they
                        are stored in the step's existing encoding (new steps:
                        plain, base64 only if the text itself is base64).
                        Platform traps: custom code takes no inputs
                        — #{name} is spliced into the source as text, so
                        splice scalars only: an indexed expression
                        (#{rows[0].x}) fails with "Mismatch in input and
                        query", and a list/object (#{rows}) arrives with broken
                        quoting (JS SyntaxError). Reduce it to a scalar first
                        (an echo step, or SQL). db_service flatData[] is an
                        array of row objects, not scalars.
                        Step output keys cannot be indexed or pathed
                        (flatData[0].col, flatData[].col): the server keeps
                        only the contract key or drops the output (verified
                        live), so wi-impl refuses them. Bind the whole output and
                        reduce it in the next step:
                          {"sql": "…", "outputs": {"rows": "flatData[]"}},
                          {"service": "Helpers.Legacy/echo",
                           "inputs": {"Input": "#{rows[0].col}"},
                           "outputs": [{"key": "response", "as": "col"}]}
                        Unset and null outputs: a method output no step writes
                        normally comes back null, but [] has been seen (e.g.
                        a draft after its writing steps were removed), so
                        don't rely on it. To return null on purpose, use
                        custom code with elementToRetrieve:
                          {"code": "console.log(JSON.stringify({x: null}))",
                           "outputs": [{"key": "x", "elementToRetrieve": "x"}]}
                        (live: x = null). Without elementToRetrieve a lone
                        custom-code output gets the whole printed object, and
                        an echo of null or #{null} returns "" (an empty
                        string), not null.
                        Stored input testValues (what the AD designer's Test
                        dialog pre-fills) are stripped by EVERY save, and wi-impl
                        cannot set them: afterwards the dialog reports
                        "Mandatory fields are not filled" until they are
                        re-entered there. wi-impl reads them first (V1) and warns
                        (data.testValuesDropped; --dry-run: testValuesAtRisk).
                        'wi-impl ad test' takes the values as inputs.

Flags:
  --uuid <UUID>         Target draft uuid (or its PUBLISHED uuid, or an AD URL). (required)
  --sql-file <N=PATH>   Replace step N's SQL with the file (repeatable).
  --code-file <N=PATH>  Replace step N's custom code with the file (repeatable).
  --dry-run             Plan + validate only; nothing is written. Returns
                        {applied, order, changes, outputsToMethod, valid,
                        validation{errors, warnings}, testValuesAtRisk}:
                        changes[{target, path, before, after}] is every field
                        the save would change (code and base64 SQL as text;
                        before/after absent = the field is added/removed);
                        order is the new step order by fetched position, new
                        steps named new#1, new#2…; outputsToMethod[{step,
                        output}] are step outputs the method returns (their
                        name is a method output). testValuesAtRisk is always
                        present ([] when none).
  --keep-case-changes   Leave the test cases as the server rewrote them on the
                        save (see step 10). Default: restore them.
  --yes, -y             Skip the confirmation prompt (required with --llm).
  --no-validate         Skip the validator. Logged loudly; not recommended.
  --strict              Validator warnings block the save too.
  --dry-run-compile     Also run the online checks (server compile dry run:
                        POSTs the executing /chain/test route with every step
                        gated off, so --dry-run then counts as a write).
  --help, -h            Show this help message.

Global Flags:
  --env <name>          Target environment. Always required, --dry-run too:
                        the dry run reads the target env, so it never falls
                        back to the default env (ENV_REQUIRED_FOR_WRITE).
  --llm                 Output structured JSON envelope for scripting/LLM use.
                        stdout carries only the JSON envelope; notices (the
                        "[wi-impl ad write] …" intent line, warnings) go to
                        stderr. Capture with `> out.json`, not `> out.json 2>&1`,
                        or the file is not valid JSON.

Pipeline and error codes:
  1. draft guard (AD_DRAFT_GUARD_*), fresh V2 GET of the draft
  2. overlay: AD_OVERLAY_UNKNOWN_KEY / AD_OVERLAY_INVALID / AD_OVERLAY_NOT_APPLIED;
     untouched steps and fields must stay byte-identical (AD_SERIALIZER_DRIFT)
     to the draft as read. One server effect is not drift: a step that calls a
     method has its output mappings read with the callee's current output
     uuids, and every publish of the callee mints new ones. So after a callee
     was republished, any save stores the new uuids for that step (same keys
     and names; `ad history diff` shows them changed). Nothing to do.
  3. validator L1–L3 (L4 with --dry-run-compile): AD_VALIDATION_FAILED with
     details {errors, warnings, blocking, layersRun, preexistingCount}
  4. confirmation (AD_CONFIRMATION_REQUIRED in --llm without --yes)
  5. freshness re-GET: AD_VERSION_CONFLICT if the draft changed since it was read
  6. POST /chain/v2: AD_SAVE_REJECTED carries the server's message
  7. re-GET verify: every value sent landed and nothing else changed (new
     steps may gain server ids/uuids/types), else AD_SAVE_VERIFY_FAILED with
     details {notLanded, unexpected, normalised}. A server normalisation is not a change: an input's
     encodedBase64 flag or a value moving between base64 and plain with the
     same decoded text (encoding), a db step's account label gaining its name
     or databaseRead.account becoming the step's account id (account), a
     condition moving between the basic and advanced form with the same
     expression (condition-form). Those are listed in
     data.normalised[{path, kind, from, to}] with a warning, and the save is
     ok with the new version
  8. compiled cache evicted on both routes, local cache dropped
  9. stored input testValues read before the save (V1 GET) and re-read after
     it; any dropped is a warning plus data.testValuesDropped
 10. test cases: every V2 save makes the server rewrite the method's persisted
     test cases (each input a case did not set becomes a raw {}; inputs the
     method no longer has are dropped). wi-impl snapshots the cases at step 5,
     compares them after the POST and PUTs every changed case back. It keeps
     only the removal of inputs the method no longer declares. Reported as
     data.testCases {changedByServer, restored, failed}; a failed restore is a
     warning. This runs before the verify (step 7), so AD_SAVE_VERIFY_FAILED
     carries details.testCases too. --keep-case-changes: report only
     (kept: true).

Data: {action, draftUuid, publishedUuid, switchedFromPublished, previousVersion,
version, applied[], unchanged[], validation{skipped, warnings, layersRun},
compiledCache{ok, uuids, routes[]}, testValuesDropped[] (always; [] when none),
testCases{changedByServer[], restored[], failed[{name, id, reason}], kept?},
normalised[{path, kind, from, to}]}.

Versions: the first V2 save of an older method (one the platform has not
migrated yet) migrates it, and the server restarts the draft's version
numbering and history at 1 (e.g. previousVersion 71, version 1; `ad history
list` then shows one version). The save landed; wi-impl warns. Confirm a save
by data.version or by content (`wi-impl ad state <uuid>` fingerprints), not
by the number going up.

Examples:
  wi-impl ad save overlay.json --uuid 4a1b2c3d... --env <env> --dry-run --llm
  wi-impl ad save --uuid 4a1b2c3d... --sql-file 3=query.sql --env <env> --yes --llm
  wi-impl ad save overlay.json --uuid 4a1b2c3d... --env <env> --code-file 2=step2.js --strict
